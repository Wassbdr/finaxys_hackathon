# Sentinel: Stage 4 Design: Final Evaluation and RESULTS.md

Date: 2026-09-24. Builds on Stages 1-3. Tags: `difficulty-frozen`, `rules-preregistered`, `simulator-v2`.

## Decisions made

| Decision | Choice | Reason |
|---|---|---|
| Uncertainty | Cluster-bootstrap 95% intervals on every metric (2,000 replicates); manipulation windows resampled by episode, normal windows by account (trader within instrument) | Windows of one episode are correlated; a few accounts (market makers) generate most false alerts |
| Comparisons | Paired differences (LightGBM minus tuned rules, textbook rules, Isolation Forest) on the same replicates | "Better" comes with an interval and a verdict |
| Headline source | Alerts from the Java engine on the seed-100 test simulation | Accuracy numbers are those of the production path |
| Isolation Forest | Scored in Python on the test features, labeled as such | It is an unsupervised comparator, not part of the Java engine |

## 1. Protocol and freeze

1. Persist the Isolation Forest threshold (previously only printed) and retrain deterministically (metrics must equal the last report).
2. Rehearse the whole pipeline on a separate fresh simulation, seed 200 (`data/rehearsal_seed200`, not the test set), so pipeline bugs surface before the single test run.
3. Freeze: sha256 (line-ending-normalised) of the model, thresholds, tuned rules, Isolation Forest and its threshold, the feature extractor, `rules.py` and the Java sources go into `docs/frozen-artifacts.json`, committed and tagged `stage4-frozen`. The final script refuses to run on a hash mismatch and prints the hashes into RESULTS.md.
4. Run on `data/test_seed100` exactly once (guarded `final=True` path, access-logged). If a bug is found afterwards, only evaluation code may change (never a model, threshold or frozen file), and the fix is recorded in RESULTS.md's run log.
5. RESULTS.md and all charts are generated by script from a JSON of results; no number is typed by hand.

## 2. What runs where

The Java engine processes the seed-100 events; its alerts (model, textbook, tuned, generic) are the headline numbers, and its per-window class probabilities drive the PR curves. The Isolation Forest is scored in Python on the same windows' features (identical to the Java features).

## 3. Metrics

Per type (SPOOFING, LAYERING, WASH) and ANY, per detector: precision, recall, F1, FPR, **episode-level recall** (was at least one window of the case flagged), recall by difficulty, average precision for score-based detectors, and alert volume (false alerts per 1,000 innocent trader-windows, and per instrument-hour of simulated time). Positives for a type are that type's windows and negatives are all NORMAL windows (other types excluded), as in the Stage 2 contract.

## 4. Charts and RESULTS.md

Charts (matplotlib, validated five-slot categorical palette, fixed detector order, direct labels sparingly, legend always, tables carry every value): precision-recall curves per type (LightGBM and Isolation Forest as curves, rules as points, the validation-chosen operating point marked); recall by difficulty with intervals; Python vs Java latency and throughput.
RESULTS.md (generated): environment, dataset sizes, main tables with intervals, paired differences, alert volume, streaming performance (from the committed Stage 3 benchmark JSON), frozen-artifact hashes and the run log.

## 5. Tests and risks

Tests: bootstrap on synthetic data with known answers (perfect detector, always-silent detector, episode-level clustering widens the interval, interval coverage across simulated worlds, paired differences); metric, PR-curve and alert-volume functions on hand-computed cases; the freeze guard refuses on a mismatch; chart and RESULTS generators produce output from a small results dict.
Risks: the test set may show something validation did not (that is its purpose; report it); hard-difficulty recall will stay low; the Isolation Forest comparison uses a different code path than the Java engine.
